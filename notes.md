Takeaway: the in-distribution 100/100 for CASE_NUMBER and BOOKING_ID does not carry over to new formats.
Case numbers only look safe because the phone rule over-matches; booking IDs leak almost every time.

**After widening the recognizers** (`app/mask.py`; held-out docs untouched):

| Type        | Before: correct / leaked | After: correct / leaked |
|-------------|--------------------------|-------------------------|
| CASE_NUMBER | 10/30 / 0                | **30/30 / 0**           |
| BOOKING_ID  | 0/30 / 28                | **30/30 / 0**           |

Changes: `PRB` and `BK` accept `-`, a space or nothing after the prefix; a bare `YYYY-NNNNNN` or
7-digit number counts only right after a label (`Case #`, `case`, `docket`, `Booking:`, `booking`),
via lookbehinds so the label is not masked. A bare 7-digit number with no label is still left alone.
`data/records` stays 100/100 with 0 leaks, over-masked policy phrases 0, and every other metric is unchanged.

Caveat: these 30 docs were used to pick the fix, so they are now a dev set, not a held-out set.
30/30 shows the fix works on these formats, not that it generalises. An honest generalisation number
needs a fresh set of formats (e.g. `Case No. 2024/001234`, `Booking ID 1234567`) scored before any tuning.

### Retrieval (`tests/test_retrieval.py`)

| Metric | Fixed 500-char chunks (28 q) | Section-aware chunks (28 q) | Section-aware (32 q) |
|--------|------------------------------|-----------------------------|----------------------|
| hit@1  | 27/28 (96%)                  | 27/28 (96%)                 | 31/32 (97%)          |
| hit@3  | 27/28 (96%)                  | **28/28 (100%)**            | **32/32 (100%)**     |

Old miss: "What is the maximum number of hours per week an employee may work in approved outside employment?"
With fixed chunks the expected `code-of-conduct.md` chunk was not in the top 8: the answer sentence
never says "outside employment", only the `## Outside Employment` heading does, and the 500-char window
cut the heading off. With the heading on every chunk it ranks 3rd (behind `remote-work.md` and
`leave-and-sick-time.md`), so it is a hit@3 but still not a hit@1.

Why it is still not a hit@1 (the only hit@1 miss):

| Rank | Chunk | Distance |
|------|-------|----------|
| 1 | `remote-work.md` > Schedule: "employees may work remotely up to 2 days per week" | 0.448 |
| 2 | `leave-and-sick-time.md` > Purpose and Scope, 220-char tail: "...urs per week ... fewer than 20 hours per week" | 0.482 |
| 3 | `code-of-conduct.md` > Outside Employment (the answer) | 0.506 |

The answer is `code-of-conduct.md` line 25 ("exceeds 20 hours per week", char 360 of a 454-char section),
stored whole with its heading, so chunking is not cutting it. The cause is word overlap: the only
distinctive term, "outside employment", is in the heading; the rest of the question ("maximum number of
hours per week", "employee may work") matches the remote-work schedule and the leave fragment better.
The answer chunk is mostly about approval, Form E-2 and conflicts, with the limit as one clause, and
MiniLM averages the whole chunk into one vector. Rank 2 is partly a chunker artifact: a short tail
piece that starts mid-word and is dense in "hours per week".

Chunk-size sweep (all 32 questions, in memory): 300/60 ranks it 2nd; 500/100, 800/150, 1200/200 and
whole sections rank it 3rd. hit@1 stays 31/32 at every size, so this is not a chunk-size problem.
Not fixed: rewording the eval question would tune the test to the system. Real fixes are hybrid
keyword + vector search (BM25 would match "outside employment" in the heading), a cross-encoder
reranker, or a stronger embedding model.

`trf` misses fewer names but not none, and it misses *different* names (the two models' misses do

#### Contacts-line rule (current)

Every policy contact is written `- **Name**, Title. Phone: ...` (27 lines, no other bold bullets).
`ContactsLineNameRecognizer` in `app/mask.py` tags the bold name as PERSON, so staff missing from the
directory are still masked. A trim step in `analyze()` keeps Markdown `*` out of NER spans
(spaCy once tagged `Cornelius Afolabi*`, which ate one bold marker).

| Names | Protection | Leaked |
|-------|------------|--------|
| Known staff (21) | deny-list + Contacts rule + NER | **0/21 (0%)** |
| Unknown names (6, held out) | Contacts rule + NER | **0/6 (0%)** |

Caveat: the 6 held-out names sit in the same Contacts format the rule targets, so 0/6 here shows
the rule works, not that names are safe everywhere. Names in prose or in other list formats still
rely on NER alone (see the fresh held-out set below).

**Decision: keep `en_core_web_lg`.** With the Contacts rule, contact names no longer depend on the
model, and both models score 100/100 on names in prose in `data/records`. `trf` would trade a
1.6-1.9x slowdown and a Python 3.14 warning for no measured gain on the current tests.

## Bugs found

- Found: Presidio skipped non-standard email domains; fixed with a custom recognizer.
- Found: spaCy NER misses some names in "Contacts" bullet lists (2/21 policy contacts). Fixed with a staff-name deny-list recognizer.
- Found: the first deny-list loaded names from the leak test's own manifest, so the 0% was guaranteed.
  Moved the list to `config/staff_directory.json` and added 6 held-out names to measure NER alone.
- Found: `.gitignore` excluded all of `data/`, so a fresh clone had no policy corpus. Now only `data/records/` is ignored.
- Found: fixed-size chunks separated answers from their section headings. Chunking by `##` section
  and prefixing the heading took hit@3 from 27/28 to 28/28 and accuracy from 27/28 to 28/28.
- Found: the prompt-level leak test never asked for contacts, so it could not see unmasked names
  in "Contacts" sections. Added 30 contact questions; unknown-name prompt leaks went from 0/152 to 3/182.
- Found: neither spaCy model catches every unfamiliar name (`lg` 3/6, `trf` 2/6 held-out names missed).
  Added a Contacts-line recognizer; unknown-name prompt leaks went from 3/182 to 0/182. Kept `lg`.
- "Outside employment" retrieval miss: fixed at hit@3 by section-aware chunking (heading on every chunk;
  hit@3 27/28 -> 28/28, accuracy 27/28 -> 28/28). Still a hit@1 miss (ranked 3rd): word overlap with
  remote-work and leave chunks, not chunk size. Next fix would be hybrid keyword + vector search.
